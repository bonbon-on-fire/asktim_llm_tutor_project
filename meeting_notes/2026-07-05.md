## Notes

### RAG chunking and lecture context

- Experiment with chunking strategy: use a whole lecture — or a whole week's lectures — as a single chunk instead of the current fixed-size chunks.
- Summarize and compress lecture material, stripping filler words down to telegraphic text, to shrink chunks and cost.
- Try to connect related lectures together intelligently so retrieval can surface material across lectures rather than one passage in isolation.
- Scope retrieval so RAG only pulls from the current week's lectures, not the whole course.
- As an alternative to retrieval, pre-seed the current week's full lecture into context.
- Lower the retrieval budget (`k`, `max_chars`) to cut cost.

### Objective RAG evaluation harness

- Set up a dedicated harness to test different versions of RAG objectively, instead of relying on the transcript grading, which is very subjective.
- No need to simulate a full transcript to test this — just run RAG on a question and evaluate the retrieved output directly.
- Build a dataset from syllabus / lecture / exercise material: choose a specific lecture and write questions pinned to a specific passage (the ground-truth chunk).
- The harness takes the dataset plus a RAG system and is widely scalable — swapping one "RAG system" variable name tests a different RAG system, so it can compare many of them.
- Score with intersection over union: how much of the ground-truth chunk is retrieved, over everything retrieved plus the ground truth.
- This is far more objective than the subjective transcript grade.

- Reading actual cost from the API response metadata is ideal; the current estimated cost accounting is fine for now, but the metadata is the goal.
